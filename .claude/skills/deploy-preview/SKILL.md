## GitHubアップロード スキル（STEP8）

> このスキルは **GitHub リポジトリ作成と作業ブランチへのアップロード**が担当です（STEP8）。
> PR作成・レビュー・マージ・共有URL発行は `github-review` スキル（STEP9）が担当します。
> 実装は `lp-implementation`、品質計測は `lighthouse-check` が担当します。

### このスキルを使うタイミング
- 実装と品質計測（Lighthouse）が済み、GitHubに上げたいとき

### 手順

**0. gh（GitHub CLI）の確認（最初に必ず行う）**
- `gh --version` でインストール済みか確認する
- **すでに入っている場合**：インストールは不要。次へ進む
- **未インストールの場合**：導入する
  ```bash
  brew install gh      # Mac (Homebrew)
  ```
- `gh auth status` で認証済みか確認する。未認証なら `gh auth login`（ブラウザ承認）
- Homebrew が無い環境などで `brew` が使えない場合は、公式（https://cli.github.com/）の案内に従う

**1. GitHub リポジトリを作成する（未作成の場合）**
- **リポジトリ作成の前に、ユーザーに必ず質問する**：
  「プロジェクト名を英語で入力してください。（例：project-a-lp）」
- 返ってきた名前を確認する：
  - 使える文字は半角英数字・ハイフン `-`・アンダースコア `_`（スペースや日本語は不可）。慣習的に小文字＋ハイフン区切り（kebab-case）が読みやすい
  - スペースや日本語が含まれる場合は、ハイフン区切りの英語に直す案を提示して確認する
- **同名リポジトリが既に存在しないか確認する**（作成の前に必ずチェックする）：
  ```bash
  # 存在すればリポジトリ情報が返り、無ければ 404 エラーになる（＝エラーが出る方が作成OK）
  gh repo view <Organization名>/<リポジトリ名>
  ```
  - **既に存在する場合**：作成せず、ユーザーに次のとおり返す
    「同じ名前のリポジトリが存在します。別の名称にしてください。」
    → 別のプロジェクト名を再度質問し、重複がなくなるまで繰り返す
  - **存在しない場合**：その名前をそのままリポジトリ名として使う
- 重複がないことを確認できたら、リポジトリを**空の状態（README等を追加しない）**で作る。すでにローカルに実装（コミット履歴）があるため、GitHub 側にファイルを足すと履歴が食い違い、後の push で衝突する。空で作ればローカル履歴をそのまま push できる
  ```bash
  # gh がある場合：Internalリポジトリを作り、現フォルダを紐付ける
  # <リポジトリ名> にはユーザーが入力したプロジェクト名（英語）を使う
  gh repo create <リポジトリ名> --visibility internal --source=. --remote=origin

  # 手動で作った場合：リモートを追加
  git remote add origin <リポジトリのURL>
  ```
  > `gh repo create` 実行時に `Name already exists on this account` 等のエラーが返った場合も、同名が存在するということなので、上記の文言でユーザーに別名を求める。

**2. アップロードしてよいか確認する**
- リポジトリの作成が完了したら、push する前に必ずユーザーに確認する：
  「リポジトリが作成できました。このプロジェクトをアップロードしますか？（YES / NO）」
  - **YES** → 手順3（push）に進む
  - **NO** → push せずに止まり、ユーザーの指示を待つ

**3. 初回アップロードも作業ブランチで push する（main には直接入れない）**
- 初回から `main` に直接 push せず、作業ブランチを切って push する（レビューを通すため）
  ```bash
  git switch -c feature/lp-initial
  git push -u origin feature/lp-initial
  ```
- push 前に秘密情報（`.env`・APIキー・トークン・`figd_` で始まる Figma トークン）が含まれていないか `git status` で確認する
- このあと STEP9（`github-review`）で PR を作成し、レビューを経て `main` にマージする
- 2回目以降の変更も同様に、作業ブランチ → PR → レビュー → マージで進める

### つまずいたときの記録
- アップロードで問題が起きたら `TROUBLESHOOTING.md` に記録する

### 完了条件（Definition of Done）
- [ ] gh がインストール・認証済み（または未使用の判断が済んでいる）
- [ ] リポジトリ名の重複を確認済み（同名が無い状態で作成した）
- [ ] GitHub リポジトリが用意されている（Internal）
- [ ] アップロード可否をユーザーに確認した（YES）
- [ ] 初回アップロードが作業ブランチで push されている（main に直接 push していない）
- [ ] 秘密情報がリポジトリに含まれていない

### 完了したら次へ
`PROGRESS.md` の STEP8 を `[x]` に更新し、`start-orchestrator` で残タスクを表示する。
その後、`github-review` スキル（PR作成・レビュー・マージ）へ進む。
共有用URL（GitHub Pages）は、PR がマージされて `main` に反映されてから STEP9 で発行する。
